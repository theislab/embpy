# Build spec: `docs/notebooks/cells.ipynb` deep dive

Target: 105-125 cells, matching the depth of `genes.ipynb` (128),
`proteins.ipynb` (89) and `small_molecules.ipynb` (175). Generated by
`scripts/notebook_generators/cells_part1..5.py`, assembled by `assemble.py`,
executed once with nbconvert on the cluster.

The notebook it replaces is 19 cells (10 markdown, 9 code, 776 words of prose,
**zero stored outputs**). It simulates 120 cells over 24 genes, which is the
root problem: scGPT, Geneformer, UCE, STATE and STACK all tokenise by *rank
over thousands of genes*, so a 24-gene input yields a near-constant embedding.
Every comparison in the current notebook is a comparison of noise. It also
`raise`s twice -- once on a missing `helical`, once when fewer than two
foundation models load -- so a reader without the optional stack gets a
traceback instead of a notebook.

## Non-negotiable house pattern

`scripts/notebook_generators/small_molecules_spec.md` states the house rules in
full and they apply unchanged: the generator skeleton, `md()`/`code()` helpers,
`r"""` unconditionally, ASCII ` -- ` and **no em dashes**, British spellings,
one `#` H1, sections `##`, subsections `###`, never `####`, GitHub anchor
cross-references, sibling notebooks by bare filename, `display(df.round(3))`
for every frame, code cells wrapped at <= ~88 chars, `CONSTANTS_IN_CAPS`
declared in the cell that first uses them, comments explaining a *decision*,
no `%` magics and no `!pip`.

Two deltas from the molecule build:

* `build_cells.sh` defaults `PY` to `uv run --no-project python`, not
  `.pixi/envs/default/bin/python`. The generators import nothing from embpy, and
  the project env cannot be resolved (`embpy[esm3]` and `embpy[helical]` have
  mutually unsatisfiable pins), so `--no-project` is the only default that works
  out of the box.
* Installation guidance is uv throughout. The current notebook's `pixi install
  -e helical-gpu` block is removed; the working env is `.venv-sc` behind the
  `embpy-sc` kernel.

Only the two evaluation sections are numbered: `## 1. scIB: does integration
preserve the biology?` and `## 2. cell-eval: is the perturbation preserved?`.

| Section | Question | Needs |
| --- | --- | --- |
| `## 1` | does integration remove the batch and keep the biology? | labels + a batch covariate |
| `## 2` | does the embedding preserve a perturbation effect? | many perturbation levels |

**Evaluation in this notebook is scIB and cell-eval, and nothing else.** embpy
also ships its own comparison metrics -- `tl.alignment_matrix` with tsi/qsi/
linear_cka/mutual_knn, `tl.knn_jaccard`, `pl.knn_label_purity`, `tl.leiden` plus
`tl.cluster_annotation_enrichment` -- and they are deliberately *not* used here.
For cells there are community-standard answers to both questions, and running a
parallel bespoke suite beside them invites a reader to average incommensurable
numbers. Those tools earn their place in `genes.ipynb`, `proteins.ipynb` and
`small_molecules.ipynb`, where no standard exists. Here they would be noise.

The concrete consequences: no cross-model agreement section, and no re-clustering
for purity -- scIB already optimises a Leiden clustering against the label to
compute NMI and ARI, so `tl.leiden` would recompute the same thing worse. The
only plots are of the scIB and cell-eval result frames themselves, plus one
orientation UMAP so the reader can see the data they are scoring.

## The datasets, and the swap-in contract

Two objects, because the two metric families ask questions that need different
experiments. Getting this wrong is the central design error the notebook exists
to avoid:

| | `adata` -- an **atlas** | `pert_adata` -- `pt.data.norman_2019()` |
| --- | --- | --- |
| used by | the sweep, `## 1` scIB, attention, decode | `## 2` cell-eval only |
| needs | cell-type labels + a **technical** covariate | many perturbation levels + a control |
| covariate is | donor, lab, technology, 10x chemistry | -- |
| source | scIB pancreas benchmark, figshare 46763269 | pertpy |
| verified shape | -- | 111,255 cells x 19,018 genes |

**scIB is an atlas-integration benchmark, not an embedding-quality score.**
Luecken et al. built it to ask whether merging batches removes the *technical*
axis while preserving the *biological* one. That makes a perturbation dataset
the wrong substrate: scoring a model highly for erasing a ctrl/stim difference
would reward it for deleting the experiment. Do not use a perturbation dataset
for `## 1`, and do not treat a treatment arm as a batch key.

Conversely `## 2` needs a perturbation dataset with many levels. cell-eval
scores agreement *per perturbation*, so with one non-control level its
discrimination metrics degenerate. `04_benchmark_models.ipynb` is the worked
example: with 7 well-separated stand-in perturbations, every discrimination
score came back exactly 1.000 for all five models, ranking nothing.

### The atlas, as measured

**scIB human pancreas** (Luecken et al. 2022), figshare file 46763269
(`scIBPancreas.h5ad`, 316 MB). Downloaded and inspected; these are observed.

`16,382 cells x 19,093 genes`. `LABEL_KEY = "celltype"` (14 islet types),
`BATCH_KEY = "tech"` (9 batches over 6 protocols: `inDrop1-4`, `celseq`,
`celseq2`, `fluidigmc1`, `smarter`, `smartseq2`).

**It is a strong integration benchmark, and the first candidate measured that
is.** Silhouette on PCA(30):

| Covariate | Global | within alpha | within beta | within acinar | within ductal |
| --- | --- | --- | --- | --- | --- |
| `celltype` (biology) | **+0.114** | -- | -- | -- | -- |
| `tech` (batch) | **+0.074** | +0.235 | +0.187 | +0.117 | +0.097 |

The batch effect is *larger within a cell type than globally*. Inside one islet
population you can still tell which protocol produced each cell, which is the
signature of a real technical nuisance rather than a covariate confounded with
biology. Contrast the alternatives measured earlier: Kang donors at **-0.042**
(and -0.065 to -0.180 within label), an injected batch at **+0.034**, a
library-depth proxy at **-0.067**.

The cause is visible in the library sizes -- median row sums by protocol run from
~4,600 UMIs (`inDrop3`) to ~1,274,900 reads (`fluidigmc1`), a 250-fold spread
with nothing to do with pancreatic biology. Say this in the notebook; it is the
clearest available illustration of what "technical covariate" means.

**Consequently the prediction `## 1` scores is the opposite of Kang's.** With a
batch silhouette of +0.074 the batch-correction block should *separate* the
models rather than saturating. Part 1 computes `WEAK_BATCH` from the measurement
and part 3 scores whichever prediction follows, so neither outcome is hardcoded.

**Nestedness 0.712** of a possible 1.78. `t_cell` (9 cells) appears only in the
inDrop runs and `smarter` contributes only four of the fourteen types, so some
labels are genuinely batch-restricted -- which is exactly what
`isolated_label_asw` measures, and the metric that no scIB table in this repo
has yet been able to compute.

**The counts, which needed checking rather than trusting.** `.X` is
log-normalised (max 13.0, non-integral). `.layers["counts"]` holds counts, but
only **57.2% of its values are integral** -- the droplet runs contribute integer
UMIs while the plate-based studies contribute *estimated* counts from transcript
quantification, which are fractional by construction (values sit at 1.002,
2.008, 4.032). scvi-tools requires integers, so the loader rounds and prints
that it did. Rounding shifts those values by under a percent. The figshare
description calls this the "full raw dataset", which is true of its provenance
and not of its dtype -- so the assertion in part 1 is what establishes it, not
the filename.

### What the atlas slot requires

Every section is still written against the contract rather than this file, so
swapping it is a one-cell edit. What `## 1` needs:

| Requirement | Why | Checked in part 1 |
| --- | --- | --- |
| >= 4 cell-type labels in `.obs[LABEL_KEY]` | every bio-conservation metric | `nunique() >= 4` |
| >= 2 technical batches in `.obs[BATCH_KEY]` | all four batch metrics, and `isolated_label_asw` | `nunique() >= 2` |
| the covariate is *technical* | scIB rewards removing it | stated, not checkable |
| batch not nested in label | otherwise "mixing batches" means "merging cell types" | measured confounding |
| raw integer counts in `.X` and `COUNTS_LAYER` | `scvi`/`scanvi` want `counts`; Geneformer ranks | `abs(X - round(X)).max() == 0` |
| unique HGNC symbols in `.var_names` | `scgpt`/`uce`/`state` are `vocab_type="symbol"` | `is_unique`, plus a vocabulary overlap audit |
| thousands of genes | rank tokenisers need them; see below | `n_vars` reported |

Part 1 measures the covariate strength rather than assuming it, because a weak
batch effect makes the batch block high and near-tied for every model -- a
column that ranks nothing. The measurement cell computes, on a throwaway PCA(30):

* silhouette of `LABEL_KEY` -- the biology available to conserve,
* silhouette of `BATCH_KEY` globally **and within each large label** -- a
  covariate that only separates between cell types is confounded with biology,
  not a nuisance,
* mean absolute deviation from uniform of the label-by-batch crosstab -- how
  nested the design is.

Report those three numbers, then state the prediction they imply for `## 1`,
and score it there. A dataset whose batch silhouette is near zero is a **weak
integration benchmark**, and the notebook must say so before quoting scores off
it rather than after.

### Norman 2019, as measured

`pt.data.norman_2019()` was downloaded and inspected; these are observed, not
assumed. **111,255 cells x 19,018 genes**, gene symbols in `.var_names`.

Three candidate perturbation columns exist and only one is usable:

| Column | Levels | Control level | Verdict |
| --- | --- | --- | --- |
| `perturbation_name` | 237 | `"control"` (11,835 cells) | **use this** |
| `guide_ids` | 237 | `""` -- the empty string | same content, unusable control label |
| `guide_identity` | 290 | none | raw guide pairs, e.g. `NegCtrl10_NegCtrl0__NegCtrl10_NegCtrl0` |

So `PERT_KEY = "perturbation_name"`, `CONTROL_VALUE = "control"`. The 236
non-control levels are single (`KLF1`) and combinatorial (`CEBPE+RUNX1T1`,
joined with `+`), which is what makes this a real test: combinatorial CRISPRa
effects are subtle and partly redundant, so the discrimination metrics have
something to fail at. Contrast with `04_benchmark_models.ipynb`, where 7
well-separated cell types produced a discrimination score of exactly 1.000 for
every model.

**Every one of the 237 levels has at least 50 cells.** So unlike the atlas, no
level needs dropping for size -- state that, because it means a `DROPPED` list
that comes back empty is a real result rather than a bug in the filter.

Two traps to handle in the loader:

* **`.X` is log-normalised, not counts** (`X.max() = 8.5`, non-integral). The
  raw counts are in `layers["counts"]`. `scvi`/`scanvi` declare
  `input_layer="counts"` and Geneformer tokenises by rank, so the loader must
  take `.X` from the counts layer -- exactly the same guard the atlas loader
  applies, and the reason it is written once as a shared step.
* **`obsm` ships `X_pca` and `X_umap`.** Delete them on load. Carrying the
  paper's embedding into a notebook that compares embeddings invites mistaking
  it for one of ours.

At 111k cells it must be subsampled. Subsample *within* perturbation so the
level set survives, and report the resulting cells-per-level distribution.

### Why a real dataset, and not a simulation

Keep this section regardless of which atlas is chosen; it is the argument for
the whole approach. The notebook being replaced simulates 120 cells over 24
genes, and every number in it is noise -- structurally, not for want of scale.
scGPT, Geneformer, UCE, STATE and STACK tokenise a cell by the *rank order of
thousands of genes*, so 24 genes yields near-identical token sequences and
therefore near-constant embeddings. Comparing near-constant embeddings compares
rounding error.

Fabricating the *covariates* fails too. Three designs were built and measured on
`pbmc3k` before this notebook committed to real data. Silhouette on PCA(30),
600 cells:

| Design | biology | injected covariate | verdict |
| --- | --- | --- | --- |
| `pbmc3k`, untouched | +0.101 | -- | no batch or perturbation exists to measure |
| injected batch, sigma = 0.5 | +0.064 | +0.034 | the covariate barely registers |
| injected batch, sigma = 1.5 | **-0.010** | +0.118 | visible only by destroying the biology |
| injected perturbation, 8x on 18 genes | +0.101 | -0.005 | invisible at every strength tried |
| library-depth tertile as batch | +0.101 | -0.067 | 0.714 confounded with cell type -- it *is* cell type |

Two reasons, both of which generalise:

* **`normalize_total` removes a library-size shift by construction.** Half the
  fabricated batch effect was a per-cell scale factor, and normalising is the
  first thing every one of these models wants. Injecting signal into a quantity
  the pipeline exists to divide out cannot survive the pipeline.
* **An effect on 18 genes out of 32,738 does not survive HVG selection.** Real
  signatures are hundreds of genes wide *and* cell-type dependent; a fixed short
  list scaled by a constant is neither, so PCA never sees it.

### The roster is not one comparison, it is three tiers

The integration section's spine, and a real confound the table must disclose
rather than average over. `ScVIToolsWrapper.__init__` takes `batch_key`
(`singlecell_models.py:1741`) and forwards it into `setup_anndata` (`:1804-1805`),
and scANVI **raises** without `labels_key` (`:1808-1812`). So the roster splits
by what each model was told:

| Tier | Models | What it saw |
| --- | --- | --- |
| told nothing | `pca`, `scgpt`, `geneformer_v2_12L`, `uce`, `transcriptformer_sapiens`, `tahoe_70m`, `state` | counts only |
| told the batch | `scvi` with `model_kwargs={"scvi": {"batch_key": ...}}` | the covariate scIB scores it on removing |
| told the labels | `scanvi` (mandatory `labels_key`) | the labels scIB scores bio-conservation on |

Run `scvi` **both ways** as two roster entries, `X_scvi` and `X_scvi_batch`.
They differ in exactly one thing -- whether the model was shown the covariate it
is scored on removing -- which makes the gap between them the only controlled
experiment in the notebook. Report `scanvi` separately from the headline table
or flag its row; its bio-conservation number is not comparable to an
unsupervised model's.

> **embpy ships scIB metrics, not integration methods.** `harmonypy`,
> `scanorama` and `bbknn` are not installed in `.venv-sc`. So what `## 1`
> measures is whatever integration each embedding model performs *implicitly*;
> there is no explicit correction step to compare against. That is a narrower
> claim than "we benchmarked integration methods" and the prose must keep it
> straight.

### Consequences for later sections

* Labels too small to appear on both sides of a split break per-label

### part 4 -- `## 2. cell-eval: is the perturbation preserved?` (target 22 cells)

This section binds to `pert_adata` (`pt.data.norman_2019()`), **not** to the
atlas. Say why in the first paragraph: cell-eval scores agreement *per
perturbation*, so it needs many perturbation levels before its discrimination
metrics mean anything, and an atlas has none. The mirror of `## 1`'s rule --
just as a perturbation dataset is the wrong substrate for scIB, an atlas is the
wrong substrate for cell-eval. `04_benchmark_models.ipynb` shows the degenerate
case: 7 stand-in perturbations, and every discrimination score exactly 1.000.

## Correctness constraints

Verified by static reading of `src/embpy` at `ccc2b9a` plus the cluster probe.

* `embedder.embed(...)` for cells: `entity_type="cell"`, `output="anndata"`,
  `preprocessing="auto"|"none"`, `key="X_<model>"`. Matrix lands in
  `.obsm[key]`; provenance in `.uns["embpy_cell_embeddings"]`, including
  `"__preprocessing__"`.
* Heavier single-cell models are reached through `embed_cells(...,
  model_kwargs=...)`, nested by model name: `checkpoint` for `state`/`stack`
  goes in `model_kwargs={"state": {"checkpoint": ...}}`, not as a top-level
  kwarg. `_get_or_load_singlecell_wrapper` forwards them to the wrapper
  constructor (`embedder.py:772`) and includes them in its cache key, so asking
  for two checkpoints of one model does not silently return the first.
* `compute_scib_metrics` is the only tl function accepting several `.obsm` keys.
  Metric columns: `nmi`, `ari`, `asw_label`, `isolated_label_asw` (batch_key
  only), `clisi`; `asw_batch`, `graph_conn`, `ilisi`, `kbet` (batch_key only);
  aggregates `bio_conservation`, `batch_correction`, `total`. Every individual
  metric is best-effort and degrades to NaN with a warning.
* `cell_eval` returns `tuple[pd.DataFrame, pd.DataFrame]`. `metric_configs` and
  `skip_metrics` are forwarded to `evaluator.compute()`; `**kwargs` goes to the
  `MetricsEvaluator` **constructor** (`skip_de=True` belongs there). Folding
  `metric_configs` into `**kwargs` raises
  `MetricsEvaluator.__init__() got an unexpected keyword argument`.
* `run_cell_eval` returns only the per-perturbation frame and writes the
  aggregate into `adata_real.uns["cell_eval_agg"]`. Its docstring's Returns
  section is right; its summary line is wrong.
* `tl.alignment_matrix` takes a `Mapping`, not an AnnData. `metric` selects the
  alignment metric; `distance` is used inside it and ignored for `linear_cka`.
  Requires >= 2 entries and identical row counts.
* `tl.knn_jaccard` is intersection/union; `k` clamps to `n-1` silently; self is
  excluded by fitting `k+1` and dropping column 0.
* `tl.leiden` overwrites `adata.obsp["distances"]`,
  `adata.obsp["connectivities"]` and `adata.uns["neighbors"]` on every call and
  has no `neighbors_key` escape. `key_added` defaults to `"leiden"`.
* `knn_label_purity` is `embpy.pl.knn_label_purity`, **not** `tl`. It returns
  `{category: purity}` plus `"__overall__"` and `"__baseline__"`, and it always
  draws.
* `phenotypic_activity` raises for any `metric` other than `"cosine"`; use
  `normalized_mean_ap`, not `mean_ap`, when group sizes differ.
* `cluster_annotation_enrichment` reads only `.obs`; enrichment is
  `in_freq / overall_freq` with no p-value and `inf` when the global frequency
  is zero.
* `tl.block_to_hidden_state_index(b) == b + 1`; `tl.block_to_attention_index(b) == b`.
* No concrete single-cell wrapper defines `extract_attention` or
  `extract_hidden_states`; all ten inherit from `SingleCellWrapper:565`/`:586`.
  `_get_layer_modules` has zero overrides in `singlecell_models.py`, so the
  base's four-name auto-detection is the only discovery mechanism.
* `has_attention` overrides exist only at `SingleCellWrapper:504` (`True`),
  `ScGPTWrapper:724` (`False`) and `StateEmbeddingWrapper:980` (`False`).
* Run on `.venv-sc` via the `embpy-sc` kernel. embpy is an **editable** install
  pointing at the cluster repo, so a pull takes effect without reinstall.
* `ScVIToolsWrapper.__init__` accepts `batch_key` (`singlecell_models.py:1741`)
  and forwards it to `setup_anndata` (`:1804-1805`); reach it through
  `embed_cells(..., model_kwargs={"scvi": {"batch_key": ...}})`. **Note the
  nesting:** `model_kwargs` is `dict[str, dict[str, Any]]` keyed by model name
  (`embedder.py:3176`, consumed at `:3407` as
  `(model_kwargs or {}).get(model_key)`), so a flat
  `model_kwargs={"batch_key": ...}` is silently ignored -- no error, and scVI
  simply never sees the covariate. `scanvi` **raises**
  `ValueError("scANVI requires labels_key ...")` without `labels_key`
  (`:1808-1812`), so it necessarily sees the cell-type labels.
* `harmonypy`, `scanorama` and `bbknn` are **not** installed: scIB *metrics* are
  available, integration *methods* are not. Do not imply the notebook could run
  a correction method.
* Target `interactive_gpu_p` (4 idle nodes, 12h limit) rather than `gpu_p`
  (nothing idle). `--partition=gpu_p --qos=gpu_priority --gres=gpu:h100:1` is
  the fallback.
* No `raise` gate anywhere. A missing backend degrades to a reported row in
  `FAILURES`, printed, and every later table states which models are absent.
